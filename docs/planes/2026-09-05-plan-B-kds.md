# Plan B — KDS de cocina: comandas, estados y pantalla 1c

> **Para agentes:** ejecutar tarea por tarea, en orden, con el ciclo de cada
> tarea completo (test que falla → implementación mínima → test que pasa →
> commit). Los pasos usan `- [x]`. Cada tarea deja software probado y
> commiteado por sí sola.

**Objetivo:** que "Enviar a cocina" cree una comanda real en Odoo, que una
pantalla fija de cocina (`/kds`, 1920×1080, superficie oscura) la muestre con
cronómetro y estación, que cocina la marque *lista* y sala la marque
*entregada*, y que el plano de salón refleje *en cocina* / *servido* desde
Odoo y no desde memoria local.

**Arquitectura:** la comanda es `restaurant.order.course` (ver ADR
`docs/decisiones/2026-09-05-cocina-sobre-cursos-odoo.md`). Un addon propio
`projectapp_kitchen` añade `ready_date`, `served_date`, `kitchen_station` y
tres métodos de servidor. En `pos/`, `lib/services/kitchen.ts` es el único que
conoce esos métodos; `lib/domain/kitchen.ts` deriva cronómetros, humores y
pestañas sin I/O; `kitchenStore` sondea cada 5 s; `components/kds/` pinta.

**Stack:** el del Plan A. Sin dependencias nuevas.

**Spec:** `docs/diseno/waiter-pantallas.dc.html` (sección `1c`) ·
`docs/diseno/waiter-design-system.dc.html` v1.1 · ADR de arriba.

## Alcance y lo que queda fuera

Dentro: enviar comanda, KDS con pestañas por estación + *Demorados*, tiempo
medio del turno, reloj, tarjetas con barra de 22 min (marcas 12/18), botón
*Listo*, columna *Listos por entregar* con *Entregado*, aviso sonoro con
*Silenciar avisos*, y los estados *en cocina* / *servido* del salón desde Odoo.

Fuera: *Historial del turno* (botón presente, deshabilitado: no hay pantalla
de historial en este plan), el botón «＋» de la tarjeta (el diseño no anota
qué hace; se omite y se pregunta), impresión de comanda, cursos numerados al
estilo Odoo (entradas / fuertes: cada envío es un curso más), y KDS sin
conexión.

## Restricciones globales

Las del Plan A (runtime, idioma, HTTP solo en `lib/services/odoo.ts`, copy por
`useTranslations`, tests ≤50 líneas / ≤7 asserts / sin condicionales /
`// Falla si …`, nunca la suite completa) más:

- **Las horas las pone el servidor.** Ningún `new Date()` viaja a Odoo.
- **`/kds` es de solo lectura salvo *Listo* y *Entregado*.** No edita pedidos.
- **Sondeo, no websockets:** 5 s. Odoo Community no expone bus a terceros sin
  módulo propio; se difiere.

## Interfaces (todas las tareas se apoyan en estas firmas)

```ts
// lib/services/kitchen.ts
export interface KitchenLine { id: number; name: string; qty: number; note: string; station: string | null }
export interface KitchenTicket { id: number; orderId: number; tableName: string; tracking: string; waiter: string; firedAt: string; readyAt: string | null; lines: KitchenLine[] }
export interface CourseSummary { orderId: number; readyAt: string | null; servedAt: string | null }
export function fireUnsentLines(orderId: number): Promise<number | null>   // id del curso o null si no había líneas nuevas
export function listKitchenTickets(sessionId: number, stationOf: (productId: number) => string | null): Promise<KitchenTicket[]>  // disparados y no entregados
export function listCompletedCourses(sessionId: number): Promise<{ firedAt: string; readyAt: string }[]>
export function listCourseSummaries(sessionId: number): Promise<CourseSummary[]>
export function markReady(courseId: number): Promise<void>
export function markServed(courseId: number): Promise<void>

// lib/domain/kitchen.ts
export type TicketMood = 'fresh' | 'normal' | 'attention' | 'late'
export function elapsedSeconds(at: string, now: number): number
export function formatClock(seconds: number): string                 // "18:40"
export function ticketMood(t: KitchenTicket, now: number): TicketMood // late ≥18 min > attention (nota) > fresh <2 min > normal
export function stations(tickets: KitchenTicket[]): string[]
export function filterTickets(tickets: KitchenTicket[], tab: string, now: number): KitchenTicket[] // 'all' | 'late' | estación
export function countTickets(tickets: KitchenTicket[], now: number): Record<string, number>
export function averagePrepSeconds(done: { firedAt: string; readyAt: string }[]): number | null

// lib/domain/tableState.ts (cambia)
export type KitchenPhase = 'none' | 'cooking' | 'ready' | 'served'
export function kitchenPhase(summaries: CourseSummary[]): KitchenPhase   // cooking si alguno sin ready; ready si todos ready y alguno sin served; served si todos served
// OpenOrder gana `kitchen: KitchenPhase`; LocalFlags pierde `sentToKitchen` y `served`.
```

## Estado: ejecutado el 2026-09-05 (rama `feat/05092026-kds`)

Desvíos respecto al plan, todos menores:

- `KitchenTicket.tableName` pasó a `tableId`: el `display_name` de la mesa en
  Odoo no es el número; el número sale del catálogo ya cargado.
- Las pestañas de estación salen de los valores de `kitchen_station` presentes
  en las comandas vivas (`Parrilla`, `Barra` en la demo), no de una lista fija.
- El E2E de cobro remoto cambió su expectativa de *Ocupada* a *En cocina*: al
  vivir la comanda en Odoo, la otra tablet ya la ve. Es el comportamiento
  buscado.
- `tracking_number` llega vacío en headless (lo pone la UI de Odoo); la
  tarjeta muestra el id del pedido.
